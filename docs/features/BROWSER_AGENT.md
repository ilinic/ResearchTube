# Browser Agent

## Public tool names

The public tool family uses `site_*`: `site_read`, `site_interact`, `site_get_files`, `site_get_children`, `site_get_node`, `site_get_text`, `site_files_status`, `site_files_cancel` and `site_session_status/pause/resume/stop`. These replace the former `browser_*` names. Reload the Extension and refresh the ResearchTube MCP catalog in ChatGPT after upgrading. Existing enabled/disabled choices migrate to the new names; an explicitly saved new-name choice takes precedence. Old tool names are not public aliases. New study prompts use the new names; existing conversations must discover the refreshed tools before continuing.

## Launch and ownership

The original [technical specification](BROWSER_AGENT_SPEC.md) is included for development continuity. Chrome 125 or later is required for flattened iframe debugger sessions.

**Study this site** in the Extension popup duplicates the exact source tab and opens a separate, ordinary ChatGPT tab in the same Chrome window. The copy uses the current Chrome profile and existing site login. The original tab is untouched. Startup clears restored text and attachments only in the exact newly created ChatGPT tab, then inserts and verifies its prompt. The source is restored after Chrome selects its duplicate; subsequent actions do not activate tabs. The popup shows exactly one filled launch button: `Describe this video` on a YouTube watch or Shorts video page, and **Study this site** everywhere else, including YouTube channels, search results and playlists.

A session owns its agent tab and dedicated ChatGPT conversation. The startup prompt supplies an opaque `sessionId` (`bas_` plus ten random URL-safe characters) for all browser calls. Users can switch active tabs or windows during initialization, observation and delivery; each operation retains the exact agent/chat tab IDs captured at session creation. It never selects a target by current focus, URL similarity or the most recently used window. Starting from an existing agent or chat tab creates an independent copy and session; it does not transfer ownership. There is no configured cap on active sessions. Conversation validation always reads the live URL of the exact owned ChatGPT tab. A delayed Chrome URL-event snapshot cannot stop or rebind a session whose actual conversation still matches. Genuine navigation to another conversation still stops the session; no replacement destination is selected. Console diagnostics include only the expected, live and event conversation paths, never query strings.

The compact startup prompt asks ChatGPT to study the site and explain useful content **in my language**. It supplies the session for every browser call, names the initial default `site_read`, incremental `site_interact` updates and relevant `site_get_files` batches. It explicitly requests downloading relevant photos and other media and attaching them to this chat for analysis, names `addToChat: true` in the call instructions, and asks the assistant to finish its response for attachment delivery before continuing. It keeps page-data and credential/identifier privacy instructions; tool descriptions carry parameter details, tab ownership and lifecycle rules.

The Extension icon shows a bright blue **AUTO** badge on the controlled agent and dedicated ChatGPT tabs, including during startup. Paused sessions retain **AUTO** with an amber background; a failed session shows **ERR** in red. Its tooltip explains the current stage. The popup contains the contextual launch button, with no session panel, errors, polling or Pause/Resume/Stop controls. Session tools remain available to ChatGPT. The studied page receives no overlay, badge, injected controls or layout changes. Camera/microphone recording indicators take precedence; Browser Agent state remains available through MCP status tools and the worker console.

CDP attaches and enables focus/lifecycle emulation before waiting for the site. Startup waits for a document body and `interactive`/`complete` readyState rather than waiting for every image, advertisement or background request. The document and ChatGPT Composer have bounded two-minute waits; cancellation is checked during document waiting. The initial prompt does not require a preliminary full AX-tree read. The first `site_read` obtains the current tree when requested. After Send, startup waits up to two minutes for the dedicated tab to receive its saved conversation address. ChatGPT’s temporary `/c/local-chatgpt%3A…` address is never bound; its replacement by the saved address is part of startup, not a conversation change. Stop and tab closure are respected during this wait. Console startup phases distinguish document waiting, Composer preparation, Send and conversation confirmation; failures retain their specific code/message.

Closing either agent or dedicated chat tab ends the session normally: `state: stopped`, `error: null`, and `stopReason.code: TAB_CLOSED`. AUTO is removed from the remaining tab. Chrome’s `target_closed` debugger event is handled the same way, even before the tab-removal event. Changing the dedicated conversation or unexpected debugger detachment still fails the session. Closing the original source tab does not. Stop clears the automation indicator and detaches the debugger, leaving tabs, attachments and saved files intact. An Extension/browser restart loses the in-memory session and task records; an old ID returns an explanatory not-found result. No tabs or sessions are invisibly recreated.

## Observation and actions

Accessibility Tree is primary. DOM is used for resource references, allowed attributes, geometry and input targets. Ordinary observation does not capture a screenshot or return full HTML. The serializer removes ignored AX nodes, redundant inline text boxes and unnamed generic wrappers while preserving meaningful hierarchy through `roots`, `parentId` and `childIds`. Child IDs outside the returned slice are deferred references, not missing tree relationships.

Start with one `site_read` call without optional limits. Its default `full` mode includes useful accessible descendants through depth 20, text and resource references in one response. `outline` remains available for a deliberate shallow view. Use `site_get_children`, `subtree` or `site_get_text` only for deferred content that is actually needed. Empty optional text/value/state/relationship fields are omitted in observations; `site_get_node` supplies full details. Long text or oversized child-reference lists are marked `truncated`; `childCount` still reports the real count.

`browserStudyMaxNodes.value` (default **200**, integer 1–1000) and `browserStudyMaxChars.value` (default **48000**, integer 1000–100000) in the single `agent/agent-config.json` set session ceilings. They are read once at launch and also bound automatic action updates. Older/offline Agents retain these defaults. Optional MCP `maxNodes` and `maxChars` may lower the ceilings, never raise them. The character budget counts serialized node structure and IDs, not just visible labels; safe page metadata and bounded change summaries add overhead. DOM media enrichment is bounded too. `depth` and `offset` control traversal and pagination. Pagination is a fresh live read: if the page revision changes, restart from offset 0 rather than treating two different page states as one snapshot. If a character budget cannot fit even one node's structure, the tool returns a clear budget error instead of an unbounded response.

`site_get_node` adds safe DOM details and resource references. `site_get_text` returns AX subtree text without duplicated inline text. Password/protected values are omitted. Page addresses and link destinations omit query strings and fragments; signed resource URLs, cookies, browser handles and physical paths are private.

`site_interact` supports click, hover, replacing editable text, named keys/key combinations, wheel scrolling and choosing native SELECT options. Actions address a current node and use CDP input. Typing verifies the actual resulting value. Custom listboxes are handled by observing and clicking their option nodes. There is no public arbitrary-JavaScript, cookie or credential-export operation.

Same-process frames are read via frame IDs. Out-of-process iframe debugger sessions are attached recursively using flattened CDP targets. A new top-level document invalidates all node/resource IDs and increments `pageVersion`. An iframe navigation/removal invalidates only that frame and known descendants, including descendants in separate debugger targets. Unrelated main-page and sibling-frame IDs remain usable. Same-document history/hash navigation updates the address and revision without discarding the document. An unchanged AX node retains its ID; replacing its backend identity, accessible action name/value or relevant state produces a fresh ID on observation. Selected targets are independently revalidated against live AX/DOM before input and resource delivery. A changed/removed selected frame or resource still blocks delivery, preserving saved files and remaining Composer attachments. In-flight frame reads cannot reinstall nodes invalidated during navigation.

Observations expose `changes`: bounded added/updated/removed node IDs, added/removed resource IDs, exact counts, `pageChanged` and summary truncation. These describe the current read relative to the last observation/action snapshot, rather than each intermediate DOM mutation. After dispatch, `site_interact` performs a local AX/DOM read and returns an `observation` containing only new and updated nodes, plus the change summary. Removed IDs need no full-page resend; unchanged nodes are omitted. Use this update directly. `observeAgain` becomes true when the update/summary was truncated, the revision advanced during the read, or the post-action read failed. `observationError` in the last case means the input was already dispatched: observe again instead of repeating the click solely for a read failure. A site may also load further asynchronous content after this snapshot; request another observation when that content is needed. No fixed action delay or promise of network-idle completion is imposed.

AX/DOM events increment the revision, and local reads reconcile the current tree. `PAGE_CHANGED` means the top-level document was replaced; `STALE_NODE` identifies the affected target instead of invalidating everything. DOM-free AX text nodes remain readable but are not actionable. Full local parsing remains inexpensive; the reduced cost comes from avoiding unnecessary model/tool round trips and repeated full-page output.

Pause blocks new mutating actions and resource requests; observation remains available. In-flight synchronous input cannot be undone. Pending resource tasks wait before delivery/Send; subsequent observations read the live page after Resume. Stop/cancel prevents later Send but cannot undo a Send already committed.

## Resources and real visual input

`site_get_files` accepts only current resource identifiers discovered in the supplied session. It cannot accept an arbitrary source URL or a caller-selected destination chat. The session fixes both the controlled source page and dedicated ChatGPT conversation. Files are saved as new Workspace artifacts without overwriting existing files. The default `addToChat:true` also attaches them and sends a continuation message to that conversation; `false` saves only. Its MCP description and parameter descriptions expose these effects explicitly. The tool remains a state-changing, non-idempotent, open-world operation with a potentially irreversible Send; it is not annotated as read-only.

`site_get_files` returns a standard `tsk_…` task immediately. Poll `site_files_status` at its `pollIntervalMs`; `site_files_cancel` is available before Send commits. Provide exactly one `resourceId` or an ordered, nonempty array `resourceIds` with distinct identifiers. Selected resources belong to exactly one session and page version. A batch is bounded by `limits.mediaToChatMaxFiles` (default 5) and saves every resource before one Composer upload and one continuation message. Status exposes `resourceIds` and ordered `files`; saved files remain listed if later extraction fails or cancellation stops the batch.

The extraction order is:

1. Original image/media/document bytes through Chrome's browser-authenticated network resource loader.
2. Browser resource cache, when available.
3. Blob/data resources or SVG/canvas rendering in the resource's DOM context.
4. Image element screenshot, clipped to the viewport.
5. Normal viewport screenshot only when no usable image element box exists.

Audio, video and document extraction fails explicitly if original bytes cannot be read; a screenshot cannot replace them. Image metadata includes the extraction method, so a rendering fallback is never represented as the original file. HTTP redirects/authentication failures may require a screenshot fallback. Files remain byte-for-byte originals whenever original extraction succeeds; no transcoding is introduced.

The Agent saves bounded bytes under `study-this-site/` using an exclusive file create. Generated filenames contain the observed resource ID with a `res_` prefix, without brackets, followed by the shared standard task ID in brackets: `res_1_8 [tsk_abcdefghij].jpg`. No date/time, separate batch number, generic `resource` name or `browser_` task prefix is added. Extension and Agent both need the compatible updated private naming protocol. `limits.mediaToChatMaxFileSizeMiB` also bounds resource extraction and this narrow binary ingestion endpoint. Formats are detected from bytes where possible. Large resources fail with the configured threshold rather than downloading an unbounded file. Original URLs/headers and private file paths never appear in MCP output.

By default, the saved file is attached through the existing CDP file chooser to the session's **exact dedicated conversation**. A minimal continuation identifies the resource and session. Attachment verification and user-edit monitoring remain active across the one authorized continuation insertion. A user draft, changed attachment or changed chat blocks Send; attachments and saved files remain. `addToChat:false` saves only. Media viewer widgets and Library storage are not used.

After requesting automatic delivery, the assistant should finish its current response so ChatGPT can enable Send. The Extension continues independently. Status polling/cancellation before Send is allowed, but no timer/status tool can independently wake a completed assistant turn. Once the browser sends the attachment plus continuation, the next turn can use the same session and inspect further resources.

## Optional timing diagnostics

`browserStudyDetailedLogging.value` in `agent/agent-config.json` is shipped as `true` for optimization. Set it to `false` to keep only the existing compact diagnostics. Grouping and this flag are read together once when a new study starts; existing sessions keep their setting. Older/offline Agents use `true`. Nothing is added to the popup or studied page.

Open the ResearchTube Extension service-worker console to collect `[ResearchTube Browser] timing` records. Each worker action starts with a visible `[YYYY-MM-DDTHH:mm:ss.sssZ]` UTC timestamp. Timing records and ordinary action details are serialized on that same text line, so DevTools Save as preserves both time and measurements without expanding objects. It includes `extensionVersion` and `atUtc` (UTC recording timestamp), plus the session, stage, event and milliseconds since diagnostic setup. `begin`/`end` pairs have a `spanId`; ends contain `elapsedMs`. Startup configuration/total durations also include the configuration lookup before setup. Startup phases cover tab creation, debugger setup, document/Composer waits, prompt preparation, enabled Send and saved-chat confirmation. `chat.queue` separates waiting for the shared automation queue from actual work.

Page tools report total duration, full AX refresh, frame/raw/indexed node counts and projection/DOM enrichment with returned node and serialized node character counts. `page.changes` records added/updated/removed node and resource counts; `page.frameInvalidated` records affected frame counts. Repeated CDP calls are summarized by method/count/total milliseconds for a span; a call taking at least 250 ms or failing also produces `cdp.slow`. CDP summaries cover the controlled site and explicitly instrumented chat startup commands, not all internal calls of shared Composer helpers. Nested/concurrent spans overlap, so do not add their durations or CDP counts as independent work.

Resource tasks report queue/extraction/save/file-resolution phases, byte count and original/cache/rendering/screenshot extraction method. `resource.chatQueue` measures waiting before attachment automation; attachment, waiting-for-Send and submission phases retain their duration, with a total on completion, failure or cancellation. Pending phases have a begin record until they finish. `tool.gap` measures time from the previous page-tool completion (or startup completion) to the next page-tool call. It includes model/client/tunnel/user waiting and possibly overlapping resource delivery; it cannot isolate model thinking time. Ordinary status polling does not produce detailed tool-timing records.

The centralized `extension/browser-diagnostics.js` handles the switch, monotonic clock, field allowlist and bounded CDP counters. It retains no log history or page/CDP bodies. Diagnostic output excludes page text, prompts, URLs, authentication data, Workspace/host paths and file bytes. Console logging failures do not alter results, tab ownership, Send or cancellation. Timing instrumentation itself only diagnoses delays. Composer file delivery separately uses the configurable readiness and acknowledgement retries described below.

## Tests and live verification

Automated tests cover strict schemas, hierarchy, pagination, safe DOM projection, original resource extraction, screenshot fallback, stream cleanup, size limits, CDP input, exact routing, navigation, iframe setup, grouping preferences, normal tab closure, simplified popup, document readiness, startup cancellation, cancellation and stop. Agent tests cover byte preservation, exclusive output creation, sandbox containment, MIME detection and request limits.

Live verification must additionally cover Chrome's actual AX/iframe behavior, authenticated resources, popup duplication and ChatGPT attachment/continuation rendering. Mocked protocol checks are not a claim that a particular external site has passed a real-browser test. Test a text site first, then a dynamic logged-in site and an image-bearing page, and finally multiple independent sessions/windows with manual navigation and Pause/Stop.

## Tab grouping

`browserStudyGroupTabs` in `agent/agent-config.json` defaults to `true`. It is read for each new Study this site session; `false` leaves both new tabs ungrouped. The Agent publishes the optional boolean in its existing internal settings response. An older or unavailable Agent uses the enabled default; invalid configuration is reported in the console. No additional Settings UI control is added.

The group contains only the two newly created tabs, uses blue and a short `RT · <page title>` name (at most 25 Unicode characters), with the hostname as an untitled-page fallback. It starts expanded so the chat is discoverable; clicking its name collapses it. Group creation failure does not prevent research. Grouping and manual moves never change the bound tab IDs. Normal session completion does not remove the group, close another tab or clear its Composer.

ChatGPT learns about closure on its next status/read/action call. Closing a tab does not automatically send a message or wake an ended assistant turn. The pending resource tasks are cancelled before Send; already saved files and attached drafts remain. A Send already dispatched is not undone. Stopping ChatGPT generation alone does not call ResearchTube session_stop or cancel an already queued delivery; closing either bound tab or invoking the appropriate MCP cancellation stops that work.

## Composer delivery retries

The shared media/file uploader reads `composerMediaRetryCount.value` and `composerMediaRetryIntervalSeconds.value` from `agent/agent-config.json` for each attachment/send operation. Defaults are **15 retries, 2 seconds apart**: an immediate check followed by up to 15 repeats, about 30 seconds plus CDP/request latency per stage. The settings accept integers 1–300 and 1–60 respectively. They apply to Browser Agent resources, `media_to_chat`, artifact `addToChat` and Library batches; no public MCP parameters are added. Older/offline Agents fall back to those defaults; malformed configuration fails explicitly.

Separate stages check file acceptance, Composer count verification before Send, enabled Send and post-click acknowledgement. An active ChatGPT response, or a temporarily missing Send control while the response UI changes, retains its existing separate bounded wait (five minutes for current-chat delivery); it does not spend the normal readiness retry budget. Focus/lifecycle emulation is enabled while automating the captured ChatGPT tab without activating that tab or selecting another one. This helps background operation but does not guarantee browser CPU priority.

Files are supplied once. The shared controller checks acknowledgement before each retry and may dispatch an enabled Send again while the expected attachment count and guarded text remain. It alternates the owning Composer form's `requestSubmit()` and trusted CDP pointer input; without a usable form it uses the pointer path. An absent or disabled Send is not clicked. Target and user-edit guards remain active before each attempt. A new user turn, started response or emptied Composer acknowledges file submission; startup also accepts the newly saved conversation address. Confirmation ends retries immediately. If the budget expires, the task fails and preserves remaining attachments and saved files. Once Send commits, cancellation cannot undo it.

Startup explicitly clears restored text and attachments in the exact newly created tab for Study this site and Describe this video, then inserts and verifies its initial prompt. It never clears another conversation. Subsequent user edits are preserved and stop further submission.

`ChatGPT Send attempt` logs attempt/maximum counts; `ChatGPT Composer form submission dispatched` identifies `requestSubmit`; `ChatGPT Send pointer target` identifies CDP input and coordinates. `ChatGPT Send not yet confirmed` records presence, disabled state, label and generation state. Only `ChatGPT Send confirmed; attempts stopped` reports acknowledgement.

Extraction and delivery are Extension-owned asynchronous work. Finishing the assistant response enables Send but does not end the worker task. Each resource is saved in Workspace before Composer receives actual file bytes. `addToChat:false` saves only; status polling does not independently wake an ended assistant turn. OpenAI safety and upload restrictions still apply.


Detailed records also emit `tab.state` checkpoints for the agent and ChatGPT tabs. They include the tab/window activity state (`active`, `windowFocused`) and page lifecycle state (`visibilityState`, `hidden`, `hasFocus`, `readyState`) without URLs, prompts or page content. The `point` field identifies the checkpoint, such as `chat.documentReady`, `resource.composerAccepted` or `resource.beforeSend`.


Composer attachment acceptance and the final pre-Send verification use only the visible attachment count. Both use the configured retry budget: an immediate check and up to 15 retries, 2 seconds apart by default. Logs contain `found`, `attachmentCount` and `expectedCount`. Filenames, types and native FileList names are not compared; a same-count replacement is allowed. A populated FileList alone does not confirm an upload. Temporary Composer remounts and count mismatches wait for the remaining retries. User text edits, cancellation and target closure/navigation stop delivery immediately; no cleanup deletes the attached files.
