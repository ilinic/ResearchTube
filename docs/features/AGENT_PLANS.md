# Individual conversation plans and shared skills

## Scope and migration
The old Scheduled Groups trigger and automatic Continue are retired. Existing browser groups remain intact and can still be used for normal Site tools. No new tasks are silently created for old groups. Ask each old scheduled chat to create its own plan with concrete tasks after upgrading. The independent one-shot timer and shared journal remain available.

## Plan
A saved ChatGPT conversation owns its queue by stable conversation ID; tab IDs are only verified routing handles. The initiating chat obtains chatTabId from system_get_chat_context. plan_read/status expose the current revision. Use plan_edit with expected_version, a stable operation_id, and actions. Example actions:
```json
[
  {"op":"add","prompt":"Inspect fresh listings and save verified results","delay_seconds":0},
  {"op":"add","prompt":"Compare the new observations with past results","delay_seconds":300},
  {"op":"add","prompt":"Review methods, update relevant skills, and plan the next experiments","delay_seconds":0}
]
```
Positions are zero-based among queued tasks; absent position appends. Edit any waiting task by numeric ID. An already sent task cannot be rewritten. History is paginated; record factual outcome with the result action. A plan may grow via repeated batches; there is no fixed queue count or application-level short delay limit. Individual text/batch/transport/database/ledger limits still apply. plan_pause pauses new dispatch, not an already running response. Empty queue stops; a chat may extend its own queue for user-authorized ongoing work.

## Scheduler
Extension checks open saved conversations every three seconds and has a 30-second alarm for worker recovery. Duplicate tabs for one conversation are skipped. A closed conversation keeps its plan; reopen it to resume. Observe actual idle state, persist the idle anchor and timestamp, wait delay_seconds, then recheck conversation, pending work, draft and plan reservation. A manual turn resets the idle delay. Never auto-send a user draft. Dispatch is durably reserved before the click; uncertain outcomes block further delivery until history confirms the marker or the paused plan is explicitly reconciled with retry/skip. Finished means an observed completed chat cycle, not verified task success. Browser shutdown, sleep, suspension, rate limits and Agent disconnection can delay delivery; no background guarantee while Chrome is closed.

## Goal, state, skills
agent_memory_write updates goal, state and skill_ids against memory_version. Keep goals user-authorized, state compact and skills reusable. Each dispatched task includes its ID and unique marker, the recorded goal and linked skill IDs/names/versions. Read relevant skill content with skill_read, not automatically as privileged instructions. Plan explicit experiments/reviews as ordinary tasks. skill_create assigns a global numeric ID, skill_update uses expected_version and retains all revisions, skill_history lists metadata and skill_read can retrieve an exact old version. Any authorized chat or local Codex can list/read/create/update skills. Chat-originated updates may include verified chatTabId for provenance; omitted provenance remains unknown. Codex records its own provenance. Skills are shared data, not trusted commands. No secrets or unrelated private information.

## Storage
All use the existing local SQLite file scheduled/database.sqlite. Protected internal tables contain plans, tasks, skills, skill versions and per-chat memory versions. The existing SqlQueue, ReadQueue and single durable Outbox worker are reused. All mutations are typed parameterized operations inside the existing transactional deduplication ledger. Internal scheduler transitions have deterministic operation IDs. Generic research SQL cannot mutate these internal tables. No new D1 migration. Transport results use JSON in data; poll/retry the same operation_id if pending or unknown, reread on version conflict. Existing database/outbox storage and ledger limits remain; split large edits into batches and read pages.

## Recovery
If plan_status shows claimed/dispatching with no confirmed delivery, inspect the actual conversation/draft. Pause the plan, explicitly retry only if safe or skip, then resume. Do not retry a potentially completed external action merely because the chat turn was interrupted.

## Conversation rollover and scheduler diagnostics
A stable agent ID is retained across conversations. The existing plan key is the agent ID; a protected mapping assigns its active conversation. Old conversations remain readable but cannot write or dispatch that plan. The Extension detects explicit maximum conversation-length UI notices, not model usage caps. For active plans in a Chrome group it opens a fresh conversation in the same group and project, sends a checkpoint/goal/skill handoff, waits for visible acknowledgement and a saved conversation ID, then atomically switches the mapping via the existing outbox. The original tab is closed only after verifying both endpoints again; the old ChatGPT conversation is not deleted. If project routing, draft safety, or confirmation fails, retain both tabs and report the blocker rather than silently redirecting. A possibly executed task becomes a reconciliation task, with original history retained. Rollover is not a full transcript clone. The browser-local recovery journal prevents blind replay after restart. Scheduler trace events PLAN_SCHEDULER_DECISION and PLAN_TRANSITION_DEFERRED identify blocks, delay, send and completion. Unbound MCP work no longer blocks every conversation; scoped operations and guarded composer checks still apply.

## Compact recurring context
Task dispatch includes Goal and current Skill references on first delivery, when their content changes or when the full-context marker is no longer visible in the previous 30 user messages. Otherwise it sends the task with a brief recovery reminder. Rollover handoffs remain complete. The agent may call agent_memory_read and skill_read with force_full=true if prior context is unavailable. plan_read, agent_memory_read and skill_read support known_version; for plan_read it must refer to the same page/history selection, and agent_memory_read still returns current Skill versions even when Goal/State are unchanged.

## Proactive context rollover
Extension Settings → Scheduled agent context rollover sets an approximate context-pressure threshold, default 224 KiB (0 disables early rollover, 128–16384 KiB enabled). The scheduler samples existing per-conversation retained transport metrics at most once a minute per active conversation, without blocking ordinary task delivery, and checks conversation text present in the DOM. It uses the larger of the two signals, not actual model tokens. Unbound calls, virtualized history and aged-out trace events can underestimate pressure. Rotate only between tasks with a nonempty saved checkpoint and queued work; hard-limit recovery remains independent. A handoff is confirmed by the exact marker followed by a nonempty assistant turn in the saved successor, not an enabled Composer. The existing agent mapping and queue are durably switched and read back before closing the original tab. Recovery also checks saved rollover journals whose original tab was closed, and can bind a confirmed successor without reopening the old conversation. Never dispatch an independent plan or delete chat history. Preserve changed documents, user drafts, attachments and in-flight actions. A checkpoint does not prove every external effect was saved; the task must record durable results as usual. Recovery cannot infer an absent journal or an unidentifiable successor.

Rollover recovery treats Chrome tab IDs as transient. When a saved conversation is reopened, the scheduler rebinds only the unique exact source conversation and a unique successor in the same current group/project with the exact acknowledged handoff marker. A legacy hard-limit journal without a source anchor may recover after the alert disappears only if its deterministic marker still matches the current plan revision, no task is running and the original chat is idle and draft-free. Ambiguous candidates, changed plans and unsafe source state block recovery. Existing queue and memory are never copied into a second agent.

Scheduled conversation inspection accepts explicit author-role nodes, structured turn containers and a fallback based on recognized You said/ChatGPT said conversation headings. Screen-reader role labels are stripped before matching the exact handoff marker. An ACK requires a user-turn marker followed by a nonempty assistant-turn response; quoted assistant markers, empty responses and intervening user requests are not accepted. The existing group/project, conversation identity, plan revision and draft checks still apply. Heading-based inspection is a compatibility fallback; live Chrome verification remains necessary.

Scheduled task completion requires positive idle Composer evidence, no generation or scoped pending operation, a nonempty assistant response following the exact task marker, and an unchanged response fingerprint across observations at least three seconds apart. A sent or visible user message alone cannot finish the task. Completion observation is bounded and in memory; after worker restart it must be established again. Interrupted turns with no answer remain uncertain and require reconciliation rather than blind replay. Every scheduled task includes the currently verified chatTabId; use it for scoped tools and explicit system_get_chat_context(chatTabId) instead of starting a widget binding. If the tab ID is rejected, reidentify the current tab. Never use an older tab ID from a checkpoint. This avoids dependence on stale widget metadata for scheduled tasks, without relaxing browser target verification.

The scheduler encourages compact website text reads by default and uses explicit full/outline only for interaction/resource access. Existing user-selected thresholds remain unchanged.
